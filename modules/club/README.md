# Модуль «Розыгрыш»

Что вышло из акции: сколько людей со страницы розыгрыша дошло до приложения и
сколько им пользуется.

Заходы на страницу считает Umami — браузерная аналитика умеет это лучше. Здесь
то, чего она не видит вовсе: участник поставил приложение или только вошёл на
сайте, открыл ли его после розыгрыша, собрал ли пару, заходит ли через неделю.

## Что считает

| Блок | Смысл |
|---|---|
| Участников | записей в `club_entries` |
| Поставили приложение | есть платформа, пуш-токен или присутствие |
| Собрали пару | непустой `users.group_ids` |
| Заходили за неделю | присутствие свежее семи суток |
| Путь участника | воронка от участия до живых через неделю |
| Откуда пришли | метка `src` из адреса: `qr`, `ig`, `tg`, `story` |
| Новички и старожилы | аккаунт заведён ради розыгрыша или был раньше |
| Последние участники | таблица с почтой, устройством и последним заходом |

## Две базы, и сводятся они питоном

Участники живут в SQLite PocketBase, присутствие — в Postgres. Зеркало
присутствия в SQLite отстаёт: 15.09.2026 из пятидесяти новейших аккаунтов в
Postgres нашлось сорок семь, а в зеркале — ноль. Считать активность по SQLite
значит показывать ноль при живых людях.

Один SQL-запрос две базы не видит, поэтому список участников читается из
SQLite, присутствие — одним запросом в Postgres по их идентификаторам, а
сводится всё в коде. Подключение к базам берётся у соседнего модуля `appdb`:
там оно уже написано правильно — только чтение, сторож по времени, ленивый
Postgres.

Отсюда же следствие: `module.json` описывает только вкладку и пути к базам,
запросов в нём нет.

## Признак «поставил приложение»

Платформу, пуш-токен и присутствие пишет только приложение — страница
розыгрыша не пишет ничего из этого. Поэтому участник без них вошёл на сайте,
но до установки не дошёл.

## Запуск руками

```
cd /opt/tessera/modules/club
APPDB_PG_DSN=... python3 main.py collect
APPDB_PG_DSN=... python3 main.py query total '{}'
```
